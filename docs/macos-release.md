# macOS updates and release validation

The first macOS update flow downloads a disk image and opens it in Finder. It does not replace a running application. After opening the DMG, quit Rikkahub, drag `Rikkahub.app` to Applications and replace the existing application, then reopen it. Application Support data and the selected data directory stay outside the application bundle.

## Architecture, version and release source

The build and updater share the asset naming rules:

| Target | Asset |
| --- | --- |
| `aarch64-apple-darwin` | `Rikkahub_<version>_mac_arm64.dmg` |
| `x86_64-apple-darwin` | `Rikkahub_<version>_mac_x64.dmg` |

The updater selects the exact current architecture and normalized SemVer. It does not choose the first DMG, guess a missing macOS download URL or extract a Linux archive. When GitHub's API cannot confirm the asset, the dialog links to the release page. SemVer prereleases sort before the corresponding stable release; build metadata does not change precedence. The full version remains in asset names and the About page; the two Apple bundle version fields use its numeric core.

This fork defaults to `P-A-N-52/rikkahub-desktop` for update checks and downloads. CI and the manual release-packaging workflow use the repository running the workflow by default. Another distributor can explicitly select its own source while building:

```bash
# Replace this example owner/repository with the intended release repository.
cd web-ui
bun run tauri:build:macos --target aarch64-apple-darwin \
  --release-repository your-org/your-fork
```

The repository is compiled into the backend; a runtime environment variable cannot redirect an installed package. A fork does not inherit the upstream Windows mirror. Keep the application identifier, release source and supported installation/upgrade path explicit before distributing a fork, particularly if it will coexist with the upstream application.

The macOS CI workflow explicitly uses its own GitHub repository as the update source. macOS builds whose current version is a SemVer prerelease also consider published prereleases, so a fork's first test release can be discovered. Stable builds keep the stable-release channel.

Downloads use unique `.part` files. A completed artifact must reach EOF, have nonzero content and match the advertised size and optional GitHub SHA-256 digest. Only then is it committed with a completion receipt. Cached installers must match the version, architecture, name, size and SHA-256 recorded in that receipt. Old files without receipts remain on disk but are downloaded again when needed; their existence alone is no longer proof of completion. Canceling or closing the dialog aborts the request and removes its partial download.

The native macOS command accepts only a matching DMG directly inside this application's updates cache. It checks the real directory, rejects symlink escapes and nonregular files, validates the completion receipt and hashes the file before invoking the absolute system `open` command. Hashing runs off the UI thread. Browser clients connected to a macOS backend use the desktop application or release page for installation; they cannot open a DMG on another computer through native IPC.

## Build records and CI

Use Bun 1.4.0, the pinned Pi commit and patches documented in [macOS development](macos.md). ARM64 and Intel are separate builds. CI uses native `macos-15` and `macos-15-intel` runners, matching the [GitHub runner reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners).

Each target produces an app ZIP, a DMG, a JSON manifest and `SHA256SUMS`. The manifest records the source commit and dirty status, source/resource hashes, Bun/Rust/Pi inputs, model catalog information, executable architecture, minimum OS load commands and signing mode. A local dirty-tree build is reviewable through those hashes; it is not evidence that its changes have been committed or released.

CI generates the public model catalog once and shares that snapshot between its two architecture jobs. The host wrapper records response sources, timestamps and hashes alongside generated-file hashes without modifying Pi's generator. Existing local generated catalogs are not regenerated by ordinary application builds. If their original responses were not captured, the manifest says so rather than inventing reproducibility evidence.

Ordinary pull requests build, test, validate and upload Actions artifacts only. Developer ID signing and notarization use a separate manually dispatched workflow with a protected environment. That workflow must run from reviewed immutable source on the main branch; configure its environment's required reviewers before use. It does not create a GitHub Release or upload release assets. Remote workflow success must be recorded from an actual run, not inferred from local YAML validation.

## Signing and notarization

The local default is ad-hoc signing. The Bun sidecar receives JIT permissions; the outer shell receives the microphone entitlement. The sidecar is signed first, followed by the app's resource seal, and the DMG is created afterward. The script never applies Bun's runtime exceptions to the outer shell or uses deep signing as a substitute for signing nested code explicitly. Bun's signing guidance and Apple's entitlement descriptions explain the runtime requirements: [Bun executable signing](https://bun.sh/guides/runtime/codesign-macos-executable), [Apple JIT entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.allow-jit).

For a reviewed release, install the appropriate Developer ID Application identity and create a notarytool keychain profile through the normal Apple workflow. Keep certificates, profile credentials and passwords outside the repository, logs and artifacts. Once those prerequisites exist, the build accepts:

```bash
cd web-ui
bun run tauri:build:macos --target aarch64-apple-darwin \
  --signing-identity 'Developer ID Application: Your Organization (TEAMID)' \
  --notarize-profile rikkahub-notary
```

Use the same intended `--release-repository` for both architectures. The notarized build verifies the signature, submits the archive, staples and assesses the app, recreates the ZIP after stapling, then signs/notarizes/staples the DMG. Any failed step fails the build. Signing without notarization, or passing an ad-hoc `codesign` check, is not equivalent to notarization. See [Tauri macOS signing](https://v2.tauri.app/distribute/sign/macos/) and [Apple notarization](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution).

Before release, verify the exact final bytes with `codesign --verify --deep --strict`, `spctl --assess`, `xcrun stapler validate`, `hdiutil verify` and the generated checksums. Install a normally quarantined download through Finder and exercise both first installation and replacement with existing data. Do not remove quarantine or bypass Gatekeeper to count that check as successful.

Intel execution under Rosetta and a cross-build are useful supplementary checks, but do not establish Intel hardware support. Neither a macOS 13 deployment target nor load-command inspection establishes runtime compatibility on macOS 13. Native Intel, minimum-OS, real-provider and remaining GUI/permission checks retain their own acceptance records.
